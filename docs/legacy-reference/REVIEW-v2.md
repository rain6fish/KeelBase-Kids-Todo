# 产品评审报告：「小计划」儿童每日学习计划管理应用

> 版本：v2.0（重写版） | 评审日期：2026-11-03
> 评审视角：产品负责人（15 年 B/C 端产品经验，含 3 年教育硬件与亲子类产品）
> 评审对象：PRD v1.0、Technical Spec v1.0、开发计划 v1.0、业务测试报告 v1.0、三端代码现状
> 评审结论：**方向成立，方案失焦。需收缩范围后进入验证期，暂不具备对外发布条件**

---

## 一、评审方法与判断依据

本次评审不重复技术审计（业务测试报告已覆盖 49 项缺陷），聚焦四个产品层问题：

| 评审维度 | 核心提问 | 结论 |
|---------|---------|------|
| 价值假设 | 谁在什么场景下、为什么非用不可 | 场景真实，但用户假设未经验证 |
| 范围控制 | MVP 边界是否支撑"最快验证" | 严重失控，三端齐上稀释投入 |
| 可度量性 | 如何判断产品做对了 | 完全缺失，无任何业务指标 |
| 交付质量 | 文档承诺与代码兑现的偏差 | 偏差大，且缺契约约束机制 |

---

## 二、总体评价

### 2.1 一句话结论

**文档水平属于优秀梯队，执行水平属于早期原型阶段。当前最大风险不是 bug 数量，而是把有限资源摊在三端上，导致没有任何一端达到"可以交给真实家庭使用"的完成度。**

### 2.2 亮点（应当保留并放大）

1. **产品价值观清晰且克制。** PRD 明确写下"帮助孩子自主管理，而非让家长盯着孩子"的红线，并识别出"变成监控工具会引发孩子抵触"这一真实风险。这在一众亲子类产品中是难得的清醒。
2. **操作流水设计有洞察。** 不可篡改的操作记录同时解决了三个问题：多家长协作的透明度、亲子之间的信任、事后复盘的依据。这是本产品真正的差异化能力，而非任务清单本身。
3. **角色与权限模型完整。** 家长 A / 家长 B 平级 + 孩子受限的三方模型，配合审批模式开关，覆盖了真实家庭的主要矛盾场景（两个家长教育理念不一致）。
4. **风险章节点得准。** 儿童隐私合规、亲子关系、家长冲突、留存四大风险全部命中，说明团队对领域有基本认知。
5. **有质量闭环意识。** 能产出 49 项带定位、带修复建议的自查报告，说明工程侧有可追溯的质检习惯。

### 2.3 关键问题（按影响排序）

#### 问题 1｜MVP 定义失真，违反"最快验证"原则（P0-产品）

- PRD 承诺 MVP 6-8 周，开发计划压到 6 周，同期交付 Flutter + Vue3 + NestJS 三端并实现"实时同步"。
- Spec 架构图直接画出 8 个微服务拆分（auth/task/note/audit/sync/notify/gamification/file），对一个家庭级工具属于明显的过度设计——即使文中注明"MVP 可合并为单体"，这种表述仍会误导排期与拆分决策。
- **结果验证了判断**：三端都建起来了，三端都是半成品。Web 端 WeekView 至今是"将在 Phase 2 中实现"的占位页；移动端 PIN 登录硬编码 `mock-family-id`，真实孩子根本无法登录；三个定时任务（提醒/超时/重复）全部是空壳方法。

> 产品判断：一个日均使用 10 分钟的家庭工具，第一版不需要三个客户端。**每多一个端，就多一份联调成本、一份一致性风险和一份无法收敛的缺陷面。**

#### 问题 2｜零用户假设验证，零业务指标（P0-验证）

四份文档中不存在：目标用户访谈记录、竞品分析、任何成功指标定义。PRD 第六章"端适配策略"、第七章"MVP 与迭代建议"都是功能视角，没有一句"我们怎么知道这个版本做对了"。

必须回答但当前未回答的问题：

- **北极星指标是什么？** 建议定为「孩子连续两周的自主任务完成率」，而非 DAU——亲子工具用 DAU 衡量会诱导错误设计。
- **6-15 岁是一个人群还是三个人群？** 小学一年级与初二学生的自主规划能力、家长介入方式、可用设备完全不同。一个产品同时服务两端，必然两头不深。
- **双端安装的转化漏斗有多陡？** 家长需注册→建家庭→给孩子装 App→教孩子 PIN 登录→孩子愿意每天打开。每一步都在流失，而文档中没有任何引导设计。

#### 问题 3｜合规被当作风险条目，而非验收标准（P0-合规）

这是儿童产品，合规不是"上线前做一次审查"，而是设计约束。当前状态：

- 手机号明文存储，项目中已存在的 AES-256-GCM 加密工具从未被引用——**能力具备但流程缺失，属于典型的管理失效而非技术不足**；
- 短信验证码只校验"是否为 6 位数字"，任意 6 位可通过，等于注册流程无门槛；
- WebSocket 无认证且全开 CORS，任何人可伪造身份订阅家庭数据。

产品侧含义：《儿童个人信息网络保护规定》要求监护人明示同意、数据最小化、可撤回。PRD 仅有"符合规定"一句，缺**监护人同意流程、数据收集清单、注销与导出路径**三件套。这三项应写入 DoD（完成的定义），不通过则版本不可对外。

#### 问题 4｜Spec 未成为唯一事实源，文档与代码两张皮（P1-流程）

典型证据：

| 现象 | 说明 |
|------|------|
| 前端调 `/auth/profile`，后端是 `/users/me` | 个人资料功能 404 |
| 前端调 `/tasks/:id/audit-logs`，后端是 `/audit-logs/tasks/:id` | 任务审计历史 404 |
| 徽章种子数据用 `streak_3`，评估逻辑只匹配 `streak` | 所有徽章永远无法授予 |
| 邀请码两处生成算法字符集不同（36 vs 32） | 同一功能两套实现 |

104KB 的 Spec 写得很全，却躺在 Docs 目录里没有进入开发流程：没有 OpenAPI 契约、没有 CI schema 校验、没有前后端联调用例。**这不是执行力问题，是流程缺位——文档没有被赋予约束力。**

#### 问题 5｜激励系统排期与自身结论矛盾（P1-留存）

PRD 第八章明确写"积分、打卡、徽章不是锦上添花，而是留存的核心手段"，但开发计划把成就/积分/奖励全部排到 Phase 2（第 7-8 周）。第一版可用产品里孩子没有任何持续打开的理由，**第一周就会流失，而流失用户不会等你的 Phase 2。**

#### 问题 6｜"假成功"比报错更伤产品（P1-信任）

`FamilySettingsView` 的移除成员操作显示成功提示但未调用任何 API；`ProfileView` 的 `color_tag` 只改本地状态。这类实现会直接摧毁用户对产品的信任——用户以为改好了，下次登录发现没变，且无从判断是 bug 还是自己操作错了。**建议列为团队红线：任何 UI 反馈必须对应真实状态变更。**

## 三、产品判断（我的取舍建议）

### 3.1 应当做减法的地方

| 项目 | 当前规划 | 建议 | 理由 |
|------|---------|------|------|
| 客户端数量 | Flutter + Web + 管理后台 | 先 Web 端（家长）+ Android 单端（孩子） | 联调成本降 40%，一致性风险收敛 |
| 离线同步 | Phase 1 内实现增量同步 + 冲突解决 | 推迟到验证留存之后 | 主场景是"在家写作业"，有 WiFi；复杂度最高、收益最低 |
| 周/月视图 | Phase 1 交付周视图 | 推迟 | 日视图 + 打卡日历足以支撑核心场景 |
| 审批模式 | Phase 1 内 | 推迟，先观察真实家庭是否需要 | 会增加孩子操作摩擦，与"自主管理"定位存在张力 |
| 微服务拆分 | Spec 中已画 8 个服务 | 明确单体 + 模块化，删除微服务表述 | 避免误导排期 |
| 多孩子支持 | Phase 3 | 保持推迟，但数据模型预留 | 二胎家庭占比高，模型必须预留 |

### 3.2 应当做加法的地方

1. **把"最简激励"提前到第一版**：连续打卡 + 星星 + 完成动效。成本约 3 人日，是留存杠杆最高的一项投入。
2. **补一页纸指标文档**：激活率、次周留存、孩子自主创建任务占比、家长备注互动率、任务完成率。
3. **补监护人同意与数据清单**：作为发布门禁。
4. **补冷启动引导**：家长建家庭 → 生成孩子邀请码 → 孩子扫码/PIN 登录，每个断点要有明确文案与容错。

### 3.3 年龄段收敛建议

v1 只服务 **6-10 岁小学生家庭**：家长参与度高、作息规律、任务类型标准化（作业/阅读/练琴/运动）。产品叙事从"让孩子自主规划"调整为"**家长逐步放权的亲子协作工具**"——这更符合该年龄段的真实决策链（付费与安装由家长决定，使用由孩子执行）。

## 四、执行建议（按优先级排序）

### 第一阶段：止血与合规（1 周）

1. 修复 5 个 P0 安全漏洞（WebSocket 认证、手机号加密、SMS 真实校验、兑换权限、Sync Push 校验）。
2. 补齐监护人同意流程与数据收集清单。
3. 清理所有"假成功"实现，改为真实调用或明确的"暂未开放"。

### 第二阶段：闭合核心链路（2 周）

4. 打通「注册 → 建家庭 → 孩子 PIN 登录 → 创建任务 → 完成 → 看到打卡」全链路，写端到端用例守护。
5. 三个定时任务（提醒/超时/重复）落地或明确下线。
6. 建立 OpenAPI 契约，加 CI 校验，消灭路径不一致类缺陷。

### 第三阶段：真实家庭验证（2 周）

7. 招募 5-10 个家庭（覆盖 1-3 年级），完成为期 2 周的封闭试用。
8. 观察指标：孩子次周留存 ≥ 40%、自主创建任务占比 ≥ 20%、家长备注互动 ≥ 3 次/周。
9. 达标后再决定是否投入激励系统 2.0、离线同步、周月视图。

### 团队协作建议

- **设立单一产品决策人**，对范围裁剪有一票否决权。当前文档中"建议加"的功能过多（PRD 第三章 3.4-3.6 全部是补充建议），缺少把它们挡在门外的机制。
- **接口契约先行**：Spec 第 5 章直接产出 OpenAPI，前后端以此为准，任何不经契约的字段变更视为缺陷。
- **Mock 台账制度**：所有 Mock（短信、PIN 登录、成员移除）登记 owner + 拆除期限，不允许无主 Mock 进入提测。

## 五、结论

| 维度 | 评分（10 分制） | 说明 |
|------|----------------|------|
| 产品定位 | 8 | 价值观清晰，场景真实 |
| 需求文档 | 8 | 结构完整，边界清楚 |
| 范围控制 | 4 | MVP 过重，三端并进 |
| 可度量性 | 2 | 无任何业务指标 |
| 合规完备度 | 3 | 有意识，无落地 |
| 交付完成度 | 4 | 核心链路未闭合，多处 Mock |
| 工程质量 | 5 | 架构合理，契约失效 |

**综合判断：产品值得做，但现在做的方式不对。** 停止新增功能，用两周把「一条链路真正跑通 + 合规门禁通过」，再用两周交给 10 个真实家庭。留存数据会告诉你要不要继续投入激励系统与离线同步——那才是决定这个产品生死的分水岭，而不是代码里还剩多少个 P2 缺陷。
